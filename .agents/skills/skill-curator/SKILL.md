# Skill 策展（skill-curator）

## 定位

- 目标：把"这次解决过"变成"下次直接命中"，减少重复踩坑和重复解释。
- 频次：**高**。每轮对话结束前扫一次；有合格候选就问，没有就静默通过，不要为凑数硬提。
- 询问有成本，所以只拿**通过筛选**的候选去问，每条控制在 3~5 行。
- 写入位置的分工：全局 = 本机主副本；项目 = **随 GitHub 传播的载体**（换设备 clone 后经验自动到位）。

## 触发信号（任一命中即进入分析）

1. 用户下达通用性指令："以后都…""不要再…""记住…""按这个格式…"。
2. 用户纠正了我的做法，或表达偏好（语言、格式、流程、验收标准、沟通方式）。
3. 同一类错误、同一命令失败出现 ≥2 次，或我第二次去查同一个东西。
4. 踩到非显而易见的坑：路径含空格/中文、编码、shell 差异、工具链怪癖、版本/API 陷阱、权限或网络限制。
5. 摸索出可复用的多步流程（构建→部署→验证、排障顺序、备份策略）。
6. 发现项目约定：目录结构、命名、文档口径、禁止事项。
7. 复盘时冒出"早知道这样会快很多"的信息。

## 反向筛选（命中即放弃，不要问）

- 一次性/易变状态：临时路径、临时端口、当天版本号（除非已写进项目文件）。
- 代码或文档一眼可得的信息，重复记录只会过期。
- 没有可操作判据的空话（"要仔细""注意质量"）。
- 敏感信息：密钥、token、cookie、隐私、内部地址。
- 与用户最新指令冲突的旧做法：先按新指令执行，再提议更新旧 skill。
- 已有 skill 完全覆盖的内容：改为"追加/修正现有 skill"，不要新建。

## 分析四问（决定是否收录、收到哪里）

1. **可复用性**：未来还会遇到几次？≥2 次才值得写。
2. **稳定性**：半年后还成立吗？依赖具体版本的必须标注版本与日期。
3. **可操作性**：能否写成"判据 + 步骤 + 反例"？写不出来就降级为项目文档备注。
4. **归属**：
   - 跨项目通用（工作方式、工具通用坑）→ **全局** skill
   - 只对当前仓库成立（构建脚本、部署步骤、目录约定）→ **项目** skill
   - 已有 skill 的主题 → **追加到该 skill**
   - 属于"事实/决策记录"而非"操作指导" → 写项目文档，不写 skill
   - 额外一问：**值不值得随仓库传播**？会复用的才落项目；纯个人偏好留在全局。

## 询问格式（一次最多 1~2 条）

```text
💡 发现可沉淀经验
- 内容：<一句话>
- 依据：<用户吩咐 / 第 N 次踩坑 / 环境怪癖>
- 建议位置：A) 全局 skill `xxx`（追加） B) 项目 skill `yyy`（新建） C) 暂不收录
- 理由：<为什么可复用>
回复 A/B/C 即可。
```

- 用户选"暂不收录"后，同一内容不再重复问，除非出现新证据。
- 用户没回应就继续当前任务，不要阻塞。
- **用户批准后再动文件**，不要先写后问。

## 写入规则

1. **位置**
   - 全局：`~/.config/opencode/skills/<id>/SKILL.md`
   - 项目：按仓库约定，`.opencode/skills/` 或 `.agents/skills/`（同一仓库只用一种）
2. **优先追加，其次新建**：新 ID 用 kebab-case，与目录同名。
3. **frontmatter 必须有 `name` 和 `description`**，描述写清"什么时候用"，否则不会被自动发现；沿用本仓库的 `whenToUse` 字段。
4. **条目格式**：`日期 + 来源（用户吩咐/实践观察）+ 判据 + 做法 + 反例/坑`。用户明确吩咐的优先级最高，标"用户裁决"。
5. **保持精简**：单个 skill 超过约 150 行就拆分或压缩，只留可执行信息。
6. **冲突处理**：新指令覆盖旧条目时就地改写，保留一句"YYYY-MM-DD 起改为…"，不要留两套互相矛盾的说法。

## 全局 + 项目双份维护

- 本 skill 同时存在于全局和项目：**全局是核心主副本，项目副本 = 核心 + 本项目专属追加**。
- 项目副本的真正用途是**随 GitHub 同步到其他设备**：全局目录只在本机，换机器就没了；仓库 clone 下来经验自动到位。
- 改核心规则必须两处都改，否则就是分叉。
- 项目专属经验（构建、部署、目录、验收）只写项目副本，不要污染全局。
- 全局副本里不出现具体仓库的路径和业务细节。
- 已有 skill 的批量搬运与跨项目分发交给 `skill-sync`，不要在本 skill 里手动逐个复制。

## 本项目专属（仅项目副本）

- 项目 skill 目录：`.agents/skills/<id>/SKILL.md`（本仓库既有约定，不要再建 `.opencode/skills`）。
- 现有项目 skill 及分工：
  - `mc-build-deploy-test`：编译、打包、部署、启动、RCON 验证的全流水线。
  - `docs-maintainer`：README/CHANGELOG 与文档口径维护、版本同步、链接校验。
  - `version-policy`：Minecraft/Fabric 版本基线与升级流程。
- 归属判断先查上面三份：能追加就追加，不要为单条经验新开 skill。
- 属于"裁决/现状"类的信息写进 `docs/实现状态.md` 的〈已裁决〉，不塞进 skill。
- 本项目副本会覆盖同名全局 skill（ID 相同则项目优先），所以核心规则必须在这里完整保留，不能指望全局兜底。
- 新条目落地位置：本项目会用 → `.agents/skills/`；本项目用不上但别处可能用 → `.agents/skill-inbox/`（由 `skill-sync` 判级）。

## 维护节奏

- 每次任务收尾（不是每轮）轻量整理：合并重复条目、删失效条目、修正过期版本。
- 发现某个 skill 过长或自相矛盾时，主动提出拆分/重写建议。
- 本 skill 自身规则也可被用户修改；改了同样同步两份。
