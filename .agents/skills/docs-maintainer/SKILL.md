# 文档维护（docs-maintainer）

## 触发

- 用户说“更新/同步/检查文档”“文档一致性”“发版”“打 tag”
- 完成一轮代码或配置变更，README/CHANGELOG/docs 可能与实现不一致
- 用户准备提交 git，但文档还没跟上

## 0. 先跑机械检查

```powershell
python tools/docs_sync.py --check
```

需要同步机械字段时：

```powershell
python tools/docs_sync.py --apply
```

- **项目版本唯一来源**：`mod/gradle.properties` 的 `mod_version`
- README 的“当前版本”、CHANGELOG 的最新条目必须与它一致
- 各文档头部的“状态：vX（日期）”是**文档修订号**，不是项目版本；内容有实质变化时手动 bump
- 《实现状态》里的“核对版本”是人工快照，只有重新核对全部条目后才能改
- 脚本还会校验 README 的本地链接，并提示 README/CHANGELOG 里的内部标识

## 1. 先裁决，再动笔

权威顺序分两层，不要混用：

| 层 | 顺序 | 用途 |
|---|---|---|
| **意图**（应该怎样） | 《需求文档》 > 《设计文档》 | 用户可见行为、边界、验收以需求为准；纯技术方案（怎么做）以设计为准 |
| **事实**（现在怎样） | 代码 > 《实现状态》 | 代码是当前行为的最终事实；实现状态必须能指向代码证据；CHANGELOG 只记录当时发布了什么 |

> 对“代码 > 实现状态 > changelog；需求文档 > 设计文档”的补充：
> 1. CHANGELOG 是 append-only 历史，不能裁决“当前行为”；旧条目错了**不改写**，只在新条目里更正。
> 2. “需求 > 设计”只适用于用户可见行为；纯技术方案以设计为准，否则需求会越权规定实现。
> 3. 实现状态是派生视图：事实跟代码，缺口判定跟需求/设计；它不反过来改需求。

**代码与需求/设计冲突时，不得为了迁就代码去改需求/设计**：要么修代码，要么把差额登记到《实现状态》。

## 2. 按读者分层写

| 文档 | 读者 | 写什么 | 不要写什么 |
|---|---|---|---|
| README | 瞥一眼的玩家/服主 | 功能一览、常用命令、安装、数据位置 | 内部编号、类名、源码路径、实现细节 |
| CHANGELOG | 玩家/服主 | 每个版本的功能变化，按「新增/修复/优化/变更/重构/文档」分组 | 同上；不写未发布内部任务清单 |
| 需求文档 | 产品/维护者 | 用户故事、边界、验收标准 | 实现现状、类名、文件路径 |
| 设计文档 | 维护者 | 技术方案、数据模型、算法、命令设计 | 实现进度结论 |
| 设计规范 | 维护者 | 代码约定、数据格式、实现约束 | 需求取舍 |
| 实现状态 | 维护者 | 未实现/未达标/文档与代码不符，附代码证据 | 功能宣传 |

**README / CHANGELOG 禁止出现**：`F-01`、`2-24`、`M4b` 这类内部编号，`ActivityRecorder` 这类类名，`*.java` 路径，内部配置键。需要追溯时放到《实现状态》，README 只留一句功能描述和链接。

## 3. 本轮流程

1. **看变更**：`git status` / `git diff`，列出本轮实际改了哪些功能、行为、数据格式、命令。
2. **跑检查**：`python tools/docs_sync.py --check`，先记录版本、链接、内部标识问题。
3. **改文档**：
   - README：只改功能与上手；状态用“可用 / 部分可用 / 规划中 / 远期”
   - CHANGELOG：在最新版本下按类别加条目；一句话一个功能点；**不引入 `[未发布]`**，除非用户明确要求
   - 实现状态：缺口、证据、优先级；删掉已修复项或标 ✅
   - 需求/设计：只改“应该怎样”；需求与设计冲突先按第 1 节裁决
   - 设计规范：代码/数据格式约定；新增约定时补章节
4. **改版本**（如有）：`mod/gradle.properties` → `python tools/docs_sync.py --apply`
5. **bump 文档修订号**：措辞 patch、增章节 minor、重构 major；日期用当天
6. **再跑检查**：`python tools/docs_sync.py --check`，必须 0 error
7. **汇报**：改了哪些文档、发现哪些矛盾、按哪条权威规则裁决、还有什么存疑

## 4. 发现矛盾时

| 矛盾 | 处理 |
|---|---|
| 代码 vs 实现状态 | 以代码为准，改实现状态；在条目里给出代码位置或可复现证据 |
| 实现状态 vs CHANGELOG | 以实现状态判断当前状态；CHANGELOG 不改历史，必要时在新条目补一句更正 |
| 需求 vs 设计（用户可见行为） | 以需求为准，改设计；若设计是有意收窄，先指出并让用户裁决 |
| 需求 vs 设计（纯技术方案） | 以设计为准；需求不规定实现细节 |
| 代码 vs 需求/设计 | 不擅自降级文档；登记为实现状态里的缺口，或修代码 |
| 无法裁决 | 停下来问用户，不要猜 |

## 5. 交付前自检

- [ ] `python tools/docs_sync.py --check` 通过
- [ ] README 没有内部编号/类名/源码路径
- [ ] CHANGELOG 最新版本 = 项目版本，条目按功能分组
- [ ] 《实现状态》里没有已修复但仍标“待办”的条目
- [ ] 需求/设计没有被代码“反向覆盖”
- [ ] 文档修订号与日期已更新（内容有实质变化时）
