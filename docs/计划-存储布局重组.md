# 计划：存储布局按「生命周期」重组（G-02 第二批）

> 2026-11-18 提案，同日服主拍板。第一批（代码层收敛）已完成：路径统一由 `StoragePaths` 解析，见 `7943b3e`。
> 本文档只讨论**业务语义**；实现按第 4 节顺序推进。

## 0. 已拍板（2026-11-18）

| 问题 | 决定 | 对布局的影响 |
|---|---|---|
| 圈地换周目 | **不删除**：换周目会产生一个旧世界，随时可以进去反复游玩 | 圈地必须留在各自世界/存档里，旧世界不清理；不做“归档后清空” |
| 轨迹 | **与方块/存档高度相关，不同周目各自保留** | 轨迹继续跟 world 走，不做跨周目聚合 |
| 乐透奖池 / 保险基金 | **跨周目滚存** | 必须移出 world，放到跨存档的共享数据区 |
| 轨迹/地图是否随世界备份 | **必须随世界备份** | 不把轨迹/地图移出 world；世界备份体积接受 |
| `globalFollowWorld` 开关 | **保留**，但只作用于“适合存存档的数据”（玩家数据、存档数据），**不包括配置** | 开关文案与作用范围要写清楚，配置永远不跟着走 |

## 1. 现在的问题（不是技术问题，是语义问题）

1. **`config/` 被当成“服务器级杂物间”**：`gold-price.json`（经济数据）、`season-advance.json`（周目进度）、`announcements.json`（公告历史）和真正的配置 YAML 混在一起。服主分不清哪些能手改、哪些改了会被覆盖。
2. **跨周目数据的边界不清**：身份/背包跨周目保留，乐透奖池/保险基金却跟 world 走，换周目等于清零——与“奖池滚存”的玩法预期冲突。
3. **调试备份写进玩家存档**：`debug claim delete backup` 落在 `world/samsara/backups/`，会被世界备份一并打包，也容易被当成玩家数据误删。
4. **`globalFollowWorld` 的作用范围没有写死**：现在容易让人以为“所有数据（包括配置）都跟着存档走”。

## 2. 拍板后的四类

| 类别 | 放什么 | 换周目 | 进世界备份 | 服主可手改 |
|---|---|---|---|---|
| `config/` 服务器配置 | 权限、命令、Web、输出模板、`web.yml`、`storage.yml` 等开关 | 保留 | 不进（单独备份） | ✅ 可以 |
| `shared/` 跨周目数据 | 身份映射、背包、乐透奖池/基金、保险基金、待领取 | **保留并滚存** | 单独备份 | ❌ 不要动 |
| `world/samsara/` 存档数据 | 圈地、容器索引、当前周目状态、轨迹、地图、活动、出生点历史、乐透当前轮次 | 跟着各自世界走；旧世界保留可进 | 进 | ❌ 不要动 |
| `backups/samsara/` 备份 | 世界备份、世界栈备份、调试删除备份、Web 审计快照 | 保留 | 不适用 | ❌ 不要动 |

一句话：**配置永远在顶层；跨周目的玩家/经济数据独立于世界；世界自己的东西（圈地、轨迹、地图）留在世界里，旧世界不删。**

### 与现状的差异（需要改的）

- **乐透奖池/基金、保险基金**：从 `world/samsara/lottery|insurance` 移到跨周目共享区，否则换周目会清零。
- **调试删除备份**：从 `world/samsara/backups` 移到 `backups/samsara/`，避免混进玩家存档。
- **`config/` 里的运行数据**（`gold-price.json`、`season-advance.json`、`announcements.json`）：归入“服务器数据”，不要和可手改配置混放。
- **`globalFollowWorld`**：只影响“跨周目数据”和“存档数据”的落点；配置与备份永远固定。

## 3. 需要明确的边界（实现前复查）

1. **旧世界可进**：换周目后旧世界的圈地、容器、轨迹、地图必须完整保留；任何“清理旧世界”的操作都要二次确认并备份。
2. **跨周目数据不能出现两份**：身份/背包/奖池在切换世界栈时必须只有一份权威数据；`globalFollowWorld` 切换仍走现有的双向迁移。
3. **备份必须自洽**：一份“完整备份”至少要包含当前 world + 跨周目数据 + 配置；恢复时三者版本要能对上。
4. **迁移失败不删旧数据**：旧位置保留，日志明确写出“哪一份是权威、哪一份是备份”。

## 4. 实施顺序

1. 先只改**新数据**的落点，旧数据原地不动（不迁移、不破坏）。
2. 加布局版本号，启动时只做一次“旧位置 → 新位置”的移动，失败则原地保留并告警。
3. 中间给一个只读的“存储布局”页：显示每类数据在哪、多大、最近写入时间，方便确认迁移结果。
4. 迁移完成且稳定一个版本后，再清理旧路径代码。

## 5. 明确不做

- 不为了“看起来整齐”搬迁运行中的世界数据。
- 不在没有备份的情况下自动删除任何旧目录或旧世界。
- 不让 Web 页面直接写 `shared/` 下的历史/经济文件。
