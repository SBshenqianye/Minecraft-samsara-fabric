## 1. 背景与目标

### 1.1 旧项目回顾

旧项目是一个 Spigot 插件，核心目标：**游戏大版本更新后自动删除白名单外的旧区块**，让新结构就近生成，玩家不用跑远图，同时保留玩家建筑。白名单机制是"旗帜圈地"：玩家放置带图案+染料的旗帜，图案映射 8 个方向、染料颜色序号映射延展距离，服务端把旗帜解析为节点，再通过线段组合并（"化线为面"）计算保护区域。

现状：**半成品，未跑通**。几何部分（Extension/Node/ChunkCoordinate）完成；`Area` 线段合并有 bug 且每次事件新建实例（字段全为 null，必然 NPE）；"化线为面"核心算法直接 `return null`；数据持久化只建文件从不读写；备份/删除功能完全没写。

### 1.2 新目标

在保留旧项目初衷（版本更新不丢建筑）的基础上，把范围扩大到**周目生命周期管理**：

1. **周目管理**：服务器按"周目"（Season）运营，可创建、开始、结束、归档周目，记录每个周目的时间与出生中心；
2. **新周目传送**：开新周目时，全员传送到距离旧出生点较远的全新位置；
3. **分组分散出生**：玩家三五成群（每组 3~5 人）围绕出生点分散在不同位置，避免开局挤在一起抢资源；
4. **活跃度分析**：分析存档"多久没有玩家来玩"，判断当前周目是否适合结束、是否该开新周目；
5. **区块管理**：保留旧项目的**旗帜多边形圈地**（继续填"化线为面"的坑），版本更新时备份 + 按白名单删除旧区块。

### 1.3 框架决策

**结论：Fabric 服务端（目标 26.1，26.2 稳定后跟进）+ 小服务端模组 + 数据包 + 离线分析脚本。**

| 框架 | 结论 | 理由 |
|---|---|---|
| Fabric | ✅ 采用 | 服务端=原版+模组，红石行为与原版一致；Carpet/Lithium/Chunky 生态；版本跟进最快；写服务端管理功能完全够用 |
| Spigot/Paper | ❌ 不采用 | 红石时序/更新顺序存在已知原版偏差，对"原版红石生存"是硬伤；Spigot 本体已被 Paper 系取代；版本跟进不如 Fabric 稳 |
| NeoForge | ❌ 不采用 | 内容模组平台，管理类工具生态弱、升级慢；仅当服务器要跑整合包（如 SkyFactory/Mechanomania）才考虑，与本服务器定位不符 |

│  数据包 (datapack)         服务端模组 (chunk-manager)     │

│  · 分组传送函数             · 出生中心/分组出生点计算       │

│                             · 白名单管理 + 删区块 + 时间倒流  │
├────────────────────────────────────────────────────────┤
│  离线分析脚本 (不开服)                                    │

**分层原则**：能用数据包做的（纯原版命令/函数）绝不写进模组；模组只做数据包做不到的（持久化状态、读 NBT、区块文件操作、定时任务）；离线脚本做"不开服就能决策"的管理分析。

## 3. 周目（Season）模型

### 3.1 核心概念

**周目 = 一个游玩纪元**，包含：编号、名称、开始/结束时间、出生中心、分组出生点、世界模式、备注。

### 3.2 世界模式（双模式，创建周目时任选）

| 模式 | 说明 | 适用 |
|---|---|---|
| **same-world** | 单世界滚动：新周目把出生中心搬到远处（距旧中心 15000~40000 格随机方向），旧建筑原地保留；周目更替走**时间倒流**（§12）退场 | 想保留旧世界且体验"逆熵"仪式感 |
| **new-world** | 新建独立世界（world_sN，**可输入种子**），旧世界完整保留并**冻结归档（不进行时空逆转）**；全员强制迁移至新世界，旧世界通过**世界栈**往返（§14） | 想要彻底新地图/新种子开局 |

> 两种模式在 `/season create` 时任选；new-world 模式下旧世界形成**世界栈**（§14），**倒流仅用于 same-world**。

### 3.3 数据模型（`config/season.json`）

```json
{
  "schemaVersion": 1,
  "currentSeasonId": 3,
  "worldStack": ["world_s1", "world_s2", "world"],   // 栈底→栈顶，栈顶 = 当前世界
  "seasons": [
    {
      "id": 1,
      "name": "S1 初探",
      "mode": "new-world",
      "worldName": "world_s1",
      "seed": 123456789,
      "startTime": 1750000000,
      "endTime": null,
      "spawnCenter": { "x": 0, "z": 0 },
      "spawnRadius": 1500,
      "groupSpawns": [
        { "x": 120, "z": -80, "playerUuids": ["uuid-a", "uuid-b"] }
      ],
      "note": ""
    }
  ],
  "settings": {
    "groupSizeMin": 3,
    "groupSizeMax": 5,
    "groupMinDistance": 1000,
    "spawnRadius": 1500,
    "spreadMinRadius": 500,
    "spreadMaxRadius": 2000,
    "newCenterMinDistance": 15000,
    "newCenterMaxDistance": 40000,
    "rewindDurationDays": 1.0,
    "birthpointJitter": 40,
    "resetIndividualBirthpoint": true
  }
}
```

> M2 补：`groupMinDistance` 默认 **1000**（组间出生点最小距离；**0 = 所有组共用出生中心**）。`newCenterMinDistance` 语义为「新中心与<b>全部历史中心集合</b>（世界初始点 + 第 1~上一次每个已开始周目的中心）都 ≥ 该值，无上限」；`newCenterMaxDistance` 仅作候选采样半径参考。`birthpointJitter` 为每个玩家独立出生点的确定性抖动（方块，0 = 同组共用组出生点）；`resetIndividualBirthpoint=true` 时把玩家系统出生点（无床死亡重生处）重置到各自的分组出生点 ± 抖动。


### 3.4 周目状态机

```
PENDING ──(create)──> ACTIVE ──(end)──> ENDED ──(archive)──> ARCHIVED
                          │
                          └──(周目钥匙持有者/公投 + admin 执行 / 活跃度判定建议)──> 触发开新周目
```

- `PENDING`：已创建未开始（只写配置，不动世界）；**解锁需"周目钥匙"（§15）或公投通过（§15.3），最终由管理员执行**
- `ACTIVE`：进行中（记录统计）
- `ENDED`：已结束（保留数据，等待归档）
- `ARCHIVED`：已归档（new-world 模式旧世界**冻结入世界栈** §14，仍可往返访问；same-world 模式仅留记录）

## 4. 新周目启动流程

`/season start`（管理员）时序：

1. **校验**：当前周目为 ACTIVE → 二次确认；**资格校验**：需"周目钥匙"（§15）或公投通过（§15.3），最终由管理员执行；可选：活跃度检查（§5）给出建议但不强制拦截；
2. **计算新出生中心 / 建新世界**：same-world = 新中心与<b>全部历史中心集合</b>（世界初始点 + 每个已开始周目中心）的距离都 ≥ newCenterMinDistance（默认 15000，可配置，无上限）；new-world = 以输入种子新建世界（world_sN）并压入世界栈（§14）；
3. **预热出生区（可选）**：调用 Chunky 或模组内预生成出生中心周围 spawnRadius 区块（否则玩家边跑边生成，体验差）；
4. **分组分配**：
   - 输入：注册玩家列表（`usercache.json` + `playerdata/`），按最后上线时间排序；
   - 组大小 3~5 人，组数 = ceil(人数 / 5)；
   - 每组生成一个出生点：围绕出生中心，极角按组序号均分 + 随机抖动，半径在 spreadMinRadius~spreadMaxRadius 之间，且组间距离 ≥ groupMinDistance（**默认 1000**；=0 则所有组共用出生中心）；
   - 出生点写入 `season.json` 的 `groupSpawns`；
   - **每人独立系统出生点**：若 `resetIndividualBirthpoint=true`，把每个玩家（无床死亡重生的默认位置）重置到各自组出生点 + 由 UUID 确定的抖动（`birthpointJitter`，默认 40，0 = 同组共用）；同组玩家因此也相差几十格，人人不同；
5. **全员传送**：逐组执行传送（数据包函数或模组内 `ServerPlayerEntity` 位移）；**保留背包/末影箱/进度**（玩家数据与 UUID 绑定，天然跨世界保留）；new-world 模式 = 强制迁移至新世界出生区，旧世界冻结归档（§14）；
6. **广播**：新周目编号、出生区坐标、玩法说明；
7. **收尾**：旧周目 `endTime` 落库、状态置 ENDED；新周目置 ACTIVE、`startTime` 落库。

> 分组出生也可临时执行（不开新周目）：`/season respawn-groups` 重新分配当前玩家分组。

## 5. 活跃度分析

### 5.1 数据来源（不开服可读）

| 文件 | 字段 | 含义 |
|---|---|---|
| `config/activity.log`（模组维护） | 时间戳 | **玩家上下线事件日志（开服期间实时追加，主数据源，M3 起）** |
| `logs/*.log(.gz)` | 日志行 | 离线兜底：解析 `joined the game` 行推断最后登录（文件名日期 + 行内时间） |
| `world/usercache.json` | `expiresOn` | 缓存过期时间 ≈ 最后登录 + 3 个月（估算级）；兼做 name↔uuid 解析 |
| `world/playerdata/<uuid>.dat` | — | ⚠️ **1.19 起 `lastPlayed`/`firstPlayed` 已从玩家数据移除**，仅旧世界存档有（已实测 1.19.2 数据无此字段） |
| `world/stats/<uuid>.json` | 各统计项 | 游玩时长（`minecraft:play_time`）、死亡数、移动/挖掘等（辅助） |
| `world/level.dat` | `LastPlayed` | 世界最后被打开/写入的时间（世界级，非玩家级） |

### 5.2 指标定义

**周目维度：**
- 最近 7 / 14 / 30 天活跃玩家数（最后登录时间落在区间内，来源见 5.1）
- 日均在线（模组统计在线时长 / 天数）
- 峰值在线（日志取 max）
- 新增玩家数（`firstPlayed` 在周目时间内；仅旧世界/统计可用）

**玩家维度分类：**
- 活跃：7 天内登录过
- 回归：14~30 天前登录过且总时长 > 阈值
- 流失：> 30 天未登录
- 沉睡：> 60 天未登录

**死服判定（建议阈值，可配置）：**
- 连续 14 天 0 人上线，且近 30 天活跃玩家数 ≤ 2 → 判定"周目已死"，提示开新周目；
- 判定结果只作为**建议**，最终由管理员决定。

### 5.3 呈现形式

1. **`/season status`**（服务端内）：当前周目 + 各项活跃度指标 + 死服建议；
2. **离线脚本 `tools/analyze.py`**（零依赖，Python 3 标准库，v0 已实现并实测）：
   - 输入：世界目录路径（或仅含 <uuid>.dat 的目录）；
   - 输出：控制台摘要 + `--json` 报告（含"距上次玩家登录 X 天"及来源标注）。
3. **可选 Web 面板**（M5）：读报告 JSON 渲染图表。

## 6. 区块管理

### 6.1 触发场景

- **场景 A（版本更新）**：MC 大版本升级后，删除未保护区块，让新结构就近生成；
- **场景 B（新周目 new-world）**：旧世界整体归档/删除（走 §3 世界模式流程）。

### 6.2 白名单体系

**两级白名单：旗帜多边形圈地（主，保留原设计）+ 配置白名单（辅）。**

#### 6.2.1 旗帜多边形圈地（主）

沿用旧项目机制：玩家放置带图案+染料的旗帜 → 图案映射 8 方向延展、染料颜色序号映射延展距离（1~16 区块）、旗帜朝向整体旋转校正（`Extension`/`Node` 逻辑保留）→ 节点产生"影响坐标集" → 节点与其影响坐标连线构成线段 → 线段集合经"化线为面"（§6.3）计算白名单区块坐标集。

#### 6.2.2 配置白名单（辅）

`config/whitelist.json`：

```json
{
  "spawnProtectionRadius": 1000,
  "regions": [
    { "name": "主城", "type": "circle", "center": {"x": 0, "z": 0}, "radius": 500 },
    { "name": "红石实验室", "type": "rect", "min": {"x": -200, "z": -300}, "max": {"x": 300, "z": 400} }
  ]
}
```

### 6.3 "化线为面"算法设计（核心）

#### 6.3.1 问题定义

输入：节点集合（旗帜所在区块坐标）+ 线段集合（节点与其影响坐标的连线），端点均为整数区块坐标，线段方向为 8 方向（正交+对角）。

输出：白名单区块坐标集 = **封闭图形（边界 + 内部）∪ 开放折线（线上所有整数格点）∪ 孤立点（单节点）**。

#### 6.3.2 格点图方案（推荐实现）

直接从"线段几何"转到"整数格点图"，天然消解斜线交叉等退化情况：

1. **线段光栅化**：对每条线段 (x1,z1)→(x2,z2)，步长 = (dx/g, dz/g)，g = gcd(|dx|, |dz|)，产出路径上所有整数格点；相邻格点之间形成 8 邻域"格点边"。例：(0,0)→(3,3) 产出 (0,0)(1,1)(2,2)(3,3)。
2. **建图**：格点集 + 格点边集构成无向图；两条斜线十字交叉时共享交点格点，自然连通，无需特殊拆分。
3. **求封闭图形（环/面）**：半边缘遍历（half-edge / face traversal）——对每个顶点按角度排序邻接边，有向边的"下一条"取目标顶点处逆时针后继，沿 next 指针走回起点得到一个面；有界面即多边形。
4. **边界点集**：组成每个有界面的全部格点。
5. **内部点集**：**扫描线填充**——对包围盒内每一行 z，求该行与所有边界边的交点（采用半开区间约定规避顶点/共线歧义），排序后成对填充。比逐点射线法快一个数量级。
6. **开放折线点集**：不在任何有界面上的线段格点（保留，作为折线保护）。
7. **孤立点**：无任何边连接的节点。
8. **并集** → 白名单区块坐标集。

#### 6.3.3 复杂度与优化

| 步骤 | 复杂度 | 说明 |
|---|---|---|
| 光栅化 | O(Σ 段长) | 每段长度即格点数 |
| 面遍历 | O(E) | E = 格点边数 |
| 扫描线填充 | O(bbox 面积 + E log E) | 每行交点排序；500×500 区块 ≈ 25 万格点，毫秒级 |

白名单生成后缓存，删除区块时按缓存判定 O(1)/区块；增量更新（局部重算）列为优化项，首版先全量重算。

#### 6.3.4 正确性用例（单测清单，纯 Java 可脱离服务端开发）

- 单个节点（孤立点）→ 只有该区块
- 单条线段（两节点）→ 线上所有格点
- 正交正方形四角 → 边界 + 内部
- 斜边菱形 → 边界 + 内部（含格点）
- 两条斜线十字交叉 → 正确连通、无重复、无悬挂
- 封闭图形 + 外伸折线 → 并集
- 相邻封闭图形共享边 → 各自内部均正确
- 凹多边形 → 内部填充正确
- 空输入 / 单线段退化 → 不崩溃

### 6.4 状态持久化与服务化（修复旧项目致命问题）

旧项目 `Area` 每次事件 `new Area()` 且字段全空（必然 NPE）、`LineSegment` 无 equals/hashCode（集合判等失效）、`createNewArea` 索引 off-by-one、数据文件只建不读写。修复方案：

- `Area` 改为**单例服务 `AreaService`**：onEnable 时从 `data/chunks.json` 加载（节点集、线段集、影响图、白名单缓存），每次变更后异步节流落盘；
- `LineSegment` 补 equals/hashCode（按端点集合相等判定）；
- 实现 `convertLineSegmentsToShape`（即 §6.3 算法）；
- 数据文件统一 JSON（替代旧 .dat 自定义格式）；
- **旗帜被拆掉**：默认保留圈地（防误拆丢范围），提供 `/cm claim rebuild` 手动重算；"拆旗即撤圈"列为待定项。

### 6.5 删除流程（维护窗口执行）

```
1. 全服公告 + 倒计时 → 停服
2. 备份：将被删除的 .mca 文件复制到 backup/purge_<时间戳>/（增量），
   可选：整档 zip（与旧项目"全面备份"一致）
3. dry-run：生成将被删除的区块列表 + 热力图（debug 图片），管理员确认
4. 执行：遍历 region/*.mca，区块坐标不在白名单 → 删除（模组内置或交给 MCA Selector 离线执行）
5. 启动：Chunky 预生成新出生区（可选）
6. 公告：新结构生成范围、注意事项
```

### 6.6 安全约束

- 删除前必须 dry-run 预览；
- 双保险：.mca 级备份 + 整档 zip；
- 提示玩家：箱子/潜影盒内容在区块文件内，会被删除；背包/末影箱/进度不依赖区块文件，安全；
- 白名单校验以区块坐标（chunkX, chunkZ）为单位，配置中的方块坐标自动取整。

## 7. 命令与权限设计

## 12. 时间倒流（逆熵引擎）

> 状态：**已实现**（档1~档3 + 倒流完成即自动物理删除，M2 迭代至 v0.8.8 完成；用户补充 2026-04，档2 提前自 M4d）。与 §3 周目（时间）、§6 区块管理（空间）共同构成项目三大主题：**空间（区块存储）/ 时间（周目轮回）/ 逆熵（世界倒流）**。

### 12.1 概念

周目重启有两种节奏：

- **瞬间重启**：更新周目时瞬间删除未圈地区块，游戏中加载时自动重新生成（游戏特性，即 §6.5 删除流程）；
- **缓慢重启（时间倒流）**：以一天为周期，未圈地区块"均匀地"回到新生成时的模样——挖过的矿道缓慢填补、人工放置的建筑缓慢消失，视觉上是"逆熵"。

### 12.2 三档实现与存储成本

| 档位 | 机制 | 存储 | 效果 |
|---|---|---|---|
| 档1 瞬间重启 | 删未圈地区块文件，加载时重生成 | 0 | 一步到位 |
| 档2 区块级波浪 | 每个未圈地区块分配一个均匀分布在一天内的"倒流时刻"，到点删除该区块（已加载则先卸载再删） | 0（只需倒流时刻表，可由白名单 + 世界文件推导） | 区块粒度"幕布式"均匀退场 |
| 档3 方块级平滑 | 记录每个被修改方块的原状态（差异库），倒流期间**按区块更改进度均匀恢复**（§12.4）；**懒加载恢复**（§12.5） | 差异库（§12.3） | 电影级：矿道填补、建筑消失 |

**实现状态**：**档1 + 档2 + 档3 已实现（M2 迭代，v0.8.8）**——`/season start` 支持倒流：未圈地块分配均匀倒流时刻（档2 区块波浪退场）+ mixin 差异库对玩家加载的区块逐格恢复（档3，懒加载；mixin 记录方块变化：玩家破坏/放置/TNT，按 §12.3 过滤世界模拟噪声，未加载区块加载时跟上）；**倒流完成即自动物理删除**（先卸载+强制保存，备份后清零区块槽，重启按当前版本重生；卸载不彻底的区块与中止倒流残留由停服窗口兜底，亦可 `rewind purge` 立即删）。未记录区域仍走删除兜底。

> 说明（针对"开了倒流区块却没删除"）：在档2 下，倒流进行中只是在内存/`rewind.json` 里把区块按时刻表**标记**为"已到点"；**物理删除在倒流完成（到期）后自动执行**（备份 + 卸载 + 清零，不再等停服）。若倒流未结束（`rewind status` 显示剩余时间>0），区块文件自然不会被删；中止倒流（`rewind abort`）后已到点区块保留、由停服窗口兜底删除或 `rewind purge` 立即删。档3 上则同时做"方块级恢复"，未记录区域仍走删区块。

### 12.3 差异库（档3需要）

**记录范围（关键决策，决定存储量级）：**

- ✅ 记：玩家破坏/放置、爆炸（TNT 等）导致的方块变化——记录"变化前的原始方块状态"；
- ❌ 不记：红石刻状态变化（活塞/灯/拉杆）、作物生长、流体流动等"世界模拟"噪声——海量且不影响"回到新模样"的主体效果。

**存储估算：**

- 单条 ≈ 位置(5B) + 原方块状态(2~4B) + 时间戳(4B) ≈ 12~20B 二进制 / 30~60B SQLite 行；
- 10 活跃玩家挖矿为主 ≈ 1万~10万次变化/天 ≈ 0.2~6MB/天 ≈ 6~180MB/月；
- 结论：**存储不是瓶颈**；真正成本是事件处理 CPU 与倒流时 setBlockState 负载（速率可配置）。

**前车之鉴**：Spigot 的 CoreProtect、Fabric 的 Ledger（[GitHub](https://github.com/QuiltServerTools/Ledger) / [Modrinth](https://modrinth.com/mod/ledger)）都用"每方块变化记录 + 回滚"模型，成熟服务器多年运行无存储问题。

**存储介质候选**：SQLite（事务可靠、可查询统计）vs 每区块二进制补丁文件（零依赖）。待定，倾向 SQLite。

### 12.4 倒流节奏：按区块更改进度均匀恢复

**档3 的倒流速率与每个区块的修改量成正比**，保证"所有区块在同一时刻（一天结束）完成倒流"：

- 设区块 C 有 N_C 条待还原记录，一天 = 1,728,000 tick（20tps × 86400s），则 C 每 tick 还原 N_C / 1,728,000 个方块；
- 频繁更改的区块（如大型矿场，N_C = 10 万）→ 每秒还原约 1 格，肉眼可见地快速回填；
- 只改过 1 次的区块 → 它的那 1 格直到一天快结束时才被还原（"不频繁更改的区块可能一天后才会有变化"）；
- 实现：每区块维护待还原 FIFO 队列 + 速率（余数累加），逐 tick 按区块轮询调度；全局每 tick 总还原量 ≈ N_total / 1,728,000，平滑有界。

> 档3 的按进度均匀恢复天然实现"全图均匀退场"，档2（区块级波浪）保留为零存储的降级方案。

### 12.5 倒流期间的行为规则（含懒加载，回应"是否全区块同时退场/性能"）

**为什么不是"全区块同时退场"：**
- 倒流是把"变化"均匀摊到整个时长里逐格恢复，不是某一秒全图瞬变。§12.4 的"按进度均匀恢复"保证每 tick 全局总还原量有界（≈ 待还原总量 / 总 tick 数），**天然避免同一 tick 全区块同时改动**导致卡顿。
- 若真"所有区块同时退场"会瞬时写几千格 + 刷屏 + 重生成——不可取。档3 通过"每 tick 全局上限 + 懒加载"规避。

**懒加载（档3，已纳入设计）：**
- 只对**玩家当前加载（loaded）的区块**做实际方块恢复，玩家眼见"现场倒流"；
- **未加载的区块不动**，只在它**被加载时**触发"恢复到该时点该有的状态"——即从差异库按当前倒流进度做一次补恢复；
- 效果：不需要对全图 21 万区块逐格恢复，只在玩家周围（view distance）内作业，性能集中且有界；未加载区零开销，加载时才"跟上时刻"。
- 配合：同一视野同时恢复的区块数有上限（如 8），超出排队；每 tick 全局还原上限（如 5000 格）防刷屏；大批量用整区块重发。

**行为规则：**
- **快照语义**（已采纳）：倒流只回滚"倒流开始时已存在的修改"，倒流期间的新改动不受影响（避免"今天建明天消"）；
- **圈地暂停**：倒流期间玩家圈地的区块立即暂停倒流，**已恢复部分保留**，剩余待还原方块冻结；
- **加载中的区块继续倒流**：玩家实时看到方块还原（特性非缺陷）。技术约束：
  - 被玩家/实体占据的方块格跳过还原（防脚下落空/窒息）；
  - 同区块大批量还原时用整区块重发代替逐格发包；
- **对未记录区域**（启用差异库前就存在的旧改动）：差异库无数据 → 用"删除/重生成"兜底（沿用档2 机制），保证未记录区也能退场，已记录区走平滑恢复，整体以"尽量平滑"为目标；
- **设计彩蛋（接受不改）**：倒流会短暂暴露矿物位置（矿道回填前可见），允许玩家"偷鸡"记忆坐标再挖。

### 12.6 与周目的衔接

- 慢倒流 = 新周目的"开场动画"：旧世界在玩家眼前退场，随后触发 §4 的传送/新出生点流程；
- 圈地（白名单）区块全程不受倒流影响；
- **倒流仅用于 same-world**；new-world 模式旧世界冻结归档、不走倒流（§14）；
- 里程碑：并入 **M4d**，依赖 M4a（白名单判定）+ M4b（服务化）+ M3（周目状态衔接）。

## 13. 远期狂想：玩偶影像（玩家倒流重放）

> 状态：**远期/实验**（用户补充，2026-04）。依赖 M4d（倒流）与记录层。

### 13.1 概念

记录玩家在周目内的动态（轨迹、动作、交互），倒流时以"影像"形式重放——**倒放**最贴合逆熵主题：玩家倒退行走、他们放置的方块在眼前拆解。玩家可**捕捉**影像，生成纪念玩偶摆进基地。

### 13.2 事实核查（已修正）

- ✅ **26.1 确实新增了原版 Mannequin（人偶/玩偶/模特）**，快照中即可用；Mojira 缺陷 [MC-306284](https://mojira.dev/MC-306284)（人偶死亡动画）证实其存在与实体特性；
- ✅ **玩家已用 mannequin 做"镜子"**（人偶显示玩家皮肤，站在对面即镜像），[TechnoSports 有报道](https://technosports.co.in/minecraft-player-creates-realistic-mirror-effects/)；Modrinth 上有 Mannequin-Stand、ketkets-mannequins、**Mannequin Mirror** 等数据包生态；
- 早期核查"26.1 无玩偶"系误判，以此为基准的设计需修正（见 13.4）。

### 13.3 记录层（便宜，周目一开始就开启）

- 每玩家采样：位置(9~12B) + 朝向(2B) + 姿态/动作(1~2B) + 时间戳(2~4B) ≈ 15~20B/条；
- 节流：仅移动/动作变化时记录，或 1 条/2~3 秒；10 玩家 × 12 小时活跃 ≈ 15~20MB/天（可压缩）；
- 存储：每玩家 append-only 二进制日志（`data/replays/<uuid>.bin`），与差异库同目录；
- **策略：录很便宜，先开着录；重放层以后做，历史数据从第一周目就开始积累。**

### 13.4 重放层（远期）

- **倒放**：轨迹逆序 + 联动方块差异库（该玩家放置的方块在倒流中消失）→ "逆熵"镜头；
- 渲染方案（按优先序）：
  a. **官方 Mannequin 实体（首选）**——26.1 原生，显示玩家皮肤、可设姿态、全客户端可见、无需客户端模组；服务端逐 tick 驱动姿态 = "提线木偶"式重放（mannequin 是画布，动作序列由服务端喂）；皮肤数据需在记录层采集（离线服注意默认皮肤问题）；
  b. 自定义"影像实体"——Fabric 服务端 + 轻量客户端模组渲染，平滑（当 mannequin 不支持连续姿态插值时用）；
  c. 盔甲架 + 玩家头颅 + 姿态——兜底，玩偶感强但动作僵硬；
- **捕捉**：玩家右键影像 → 生成"纪念玩偶"（就是一个带该玩家皮肤/姓名的 mannequin 或对应物品，NBT 存皮肤 + 玩家名 + 时间戳），可摆进基地当周目纪念品——**与"镜子"玩法同源**（同一个 mannequin 机制，一边当镜子一边当纪念品）；
- 性能：同一视野内影像数量上限（如 8 个），优先放送高价值轨迹（死亡、大型建造、首次击杀等事件高亮）。

### 13.5 里程碑与风险

- 并入 **M6（远期/实验）**，依赖 M4d 与记录层；
- **M6 前期技术验证点**：26.1 mannequin 的能力边界——能否程序化设置皮肤/姿态、能否逐 tick 驱动（提线木偶式）、离线服皮肤数据来源；
- 风险：mannequin 姿态驱动能力未验证（若不行则回退方案 b/c）、数据量、玩法价值不确定 → 先做记录层（零风险，从第一周目开始录），重放层小步验证。

## 14. 世界栈（双世界模式与跨世界传送）

> 状态：规划中（用户补充，2026-04）。

### 14.1 概念

开新周目时，**保留世界 / 新世界两种模式任选**：

- **same-world**：单世界滚动，周目更替走时间倒流（§12）；
- **new-world**：新建独立世界（**可输入种子**），旧世界完整保留并**冻结归档（不进行时空逆转）**，全员强制迁移至新世界（保留身上物品与末影箱），旧世界通过**世界栈**往返访问。

### 14.2 世界栈模型

- 世界按周目叠放成**栈**：最新世界 = 栈顶，旧世界依序压栈（world_s1、world_s2、world）；
- 每层独立文件夹、独立种子、独立下界/末地；
- `season.json` 维护 `worldStack`（栈底→栈顶）与当前世界指针（§3.3）。

### 14.3 跨世界往返（方案 A：用户初稿）

- **下（新世界 → 旧世界）**：在新世界**下界**基岩天花板（Y≈127）往下打穿/潜行 → 传送到旧世界对应坐标（下界坐标 × 8，标准下界→主世界比例）；
- **上（旧世界 → 新世界）**：在旧世界**主世界**搭方块/破基岩到 Y>320 → 传送到新世界对应 XZ 的 Y≈4 基岩上（下层基岩最上方）；
- 多个旧世界 = 栈：逐层上/下，一次一层。

**方案 B（对称备选，开发时二选一或都做）**：全部走主世界纵轴——每层主世界 Y=0 基岩向下挖 → 下层世界 Y≈320 顶部；Y≈320 向上 → 上层世界 Y≈4。同 XZ、无 ×8 换算，心智模型统一为"垂直层叠世界"。

### 14.4 强制迁移

- 新周目开始时全员传送至新世界出生区；**背包/末影箱/进度天然保留**（玩家数据与 UUID 绑定，不随世界文件）；
- 旧世界默认不限制访问（自由往返）；是否限制（如只读/限时）待定。

### 14.5 实现要点

- 传送触发：模组监听基岩层方块交互/破坏 + Y 阈值区域检测 → 目标世界加载 + 安全落点查找（防掉落虚空）；
- 多世界加载：模组自管理世界加载/卸载（Fabric 服务端多世界）；
- 世界栈数据结构与 season.json 持久化（§3.3）。

## 15. 抽象成就与周目资格

> 状态：规划中（用户补充，2026-04）。

### 15.1 概念

"抽象概念成就" = 服务端自定义**里程碑**（区别于游戏内成就系统）：**首个达成**的玩家获得**开新周目资格**（"周目钥匙"）；另有公投通道（§15.3）。

### 15.2 里程碑注册表（config/milestones.json）

```json
{
  "milestones": [
    { "id": "first_wither", "name": "第一个击杀凋灵", "criteria": { "type": "stat", "stat": "minecraft:kill_entity.minecraft:wither", "min": 1 } },
    { "id": "first_netherite", "name": "第一套下界合金", "criteria": { "type": "advancement", "advancement": "minecraft:nether/netherite_armor" } }
  ]
}
```

- 判定源：stats（统计）/ advancement（进度触发）/ scoreboard（计分板）；
- 首个达成 = 全局仅颁发一次，holder 玩家 + 时间戳记入 season.json 与编年史；
- **协同**：里程碑时刻 = 玩偶影像的高光重放素材（§13.4）与活跃度信号（§5.2）。

### 15.3 周目资格与公投

- **周目钥匙**：首个达成里程碑的玩家获得（season.json 标记 + 纪念物品），可发起开新周目；
- **公投**：`/season vote`，48 小时内活跃玩家 ≥60% 赞成则通过；
- 最终执行权在管理员（`/season start` 需 season.admin）。

### 15.4 与活跃度关系

"当前周目长时间无新里程碑达成"作为死服判定的辅助信号。

## 16. 正版/离线身份同步

> 状态：规划中（用户补充，2026-04）。

### 16.1 问题本质

- 在线模式 UUID = Mojang 实名；离线模式 UUID = `UUID.nameUUIDFromBytes("OfflinePlayer:" + 名字)`；
- 切换 online-mode 后同一人变成两个 UUID → playerdata/stats/advancements 分裂，宠物 OwnerUUID 指向旧 UUID → **"狗不认识我"**。

### 16.2 方案：身份映射表 + 一次性迁移

- **映射表** `data/identity_map.json`：`{ name → { offlineUuid, onlineUuid, canonicalUuid } }`，任何模式登录时自动维护；
- **存储规范化**：玩家数据统一以 canonicalUuid 读写（读写路径按映射翻译）；
- **切换模式时** `/identity migrate`（管理员）：
  1. 按映射迁移离线 UUID 的 playerdata/stats/advancements → 规范 UUID（改名/合并，新数据优先）；
  2. **宠物认主改写**：后台分区块扫描实体，将 OwnerUUID（狗/猫/马等）从旧 UUID 改写为新 UUID；
- 离线服皮肤另配皮肤模组/服务（与本功能解耦）。

### 16.3 安全提示

离线模式无身份认证，任何人可冒名顶替名字 → 映射会把冒名者视为同一人（朋友圈服可接受）；如需更严格可加"绑定码"（可选）。
