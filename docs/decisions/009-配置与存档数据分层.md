# 009 · 配置与存档数据分层

- 日期：2026-10-30
- 状态：已裁决（规划 v0.18 实施）
- 相关：`docs/需求文档.md` F-118~F-122、`docs/设计文档.md`〈配置与数据分层〉、`docs/设计规范.md`〈文件布局〉

## 背景

v0.17.0 之前，模组所有数据都放在 `config/samsara/`：既有 `commands.json` 这类服主配置，也有 `season`、`claims`、`diff`、`track`、`activity`、`backups` 这类随存档产生的世界数据。

这带来三个问题：

1. **语义混乱**：删配置、重置配置时容易误删世界数据；备份配置时又会把几十 GB 的轨迹/差异一起带走。
2. **存档不可携带**：复制 `world/` 到另一台服务器，周目、圈地、轨迹不会跟着走。
3. **世界栈冲突**：多个世界共用同一套 `config/samsara/`，只能靠路径里的 `<世界>` 层区分，容易串数据。

## 决策

采用三层根目录：

| 层 | 默认位置 | 内容 | 随存档 |
|---|---|---|---|
| 配置 | `config/samsara/` | 命令开关、权限、粒子、存储覆盖、Web | 否 |
| 世界数据 | `<存档根>/samsara/` | 周目、圈地、倒流、轨迹、回看、备份、活动、审计 | 是 |
| 全局数据 | `<存档根>/samsara/global/` | 身份映射、认证、跨世界审计索引 | 是（默认） |

- 世界数据根由 `MinecraftServer.getWorldPath(LevelResource.ROOT)` 解析，专用服务器是 `world/`，单人存档是 `saves/<存档名>/`。
- 世界栈的每个世界目录各自拥有 `samsara/`，不再需要路径里的 `<世界>` 层。
- 全局数据默认也随存档：安装本模组的服务器通常不会频繁换存档，转移存档时通常也希望身份/认证一起走。
- 为了自由性，`storage.globalFollowWorld`（默认 `true`）允许把全局数据改为服务器级 `<服务器根>/samsara/global/`；切换开关时程序在两种位置之间双向迁移，不要求服主手动搬文件。
- 旧 `config/samsara/` 数据启动时幂等迁移，迁移前备份、失败不删源、写版本标记，旧目录改名 `config/samsara.legacy` 保留一份。

## 为什么不是其它方案

- **继续全放 `config/samsara/`**：无法随存档走，且配置与数据无法安全地分别备份/清理。
- **全部随存档（包括权限/命令开关）**：复制存档会把服主的权限和命令开关带到另一台服务器，容易出现越权或行为不一致。
- **全局数据强制随存档**：多存档共用同一套身份/认证时，每个存档各一份会分裂；因此保留 `globalFollowWorld=false` 的服务器级选项。
- **全局数据强制服务器级**：转移存档时身份/认证不会跟着走，违背“存档可携带”的默认目标。
- **全部放服务端根目录 `samsara/data/`**：存档复制不携带数据，违背“随存档走”的目标。
- **每个世界一个独立全局目录**：世界栈删除/回滚时容易留下孤儿数据；随存档更自然。

## 后果

- 存档备份会包含模组世界数据（体积变大），需要在 README/运维文档里说明；备份保留策略继续限制 `purge_*`/`compact_*` 数量。
- `config/samsara.legacy` 会短期占用一份旧数据空间，确认迁移成功后可手动删除。
- 所有模块必须通过统一的 `StoragePaths` 取路径，禁止各自拼 `config`；否则会重新长回旧布局。
- `globalFollowWorld` 切换需要暂停身份/认证读写并做双向迁移；Web 状态页必须显示当前方向与迁移结果。
- 测试需覆盖：全新安装、旧 JSON、旧数据目录、已迁移、迁移失败、目标冲突、复制存档到新服务器、`globalFollowWorld` 双向切换。
